# Sub-agent 复杂任务正交拆解与并发调度工程指南

> **挂载边界约束**：**本技能仅且必须挂载在【主控 Agent (CPH-Main)】中**。子代理（Researcher / Coder）不挂载此技能，从物理和心智上杜绝孙代理递归。

---

## 核心原则 (Core Principles)

1. **会话独立与配额倍增**：每个子任务派发给全新的独立会话，享有专属的 30 轮推理黄金期与干净上下文；
2. **显式角色与最小权限**：每个子任务必须显式指定为 `researcher`（别名 `searcher`）或 `coder`，Harness 按角色路由不同 Agent 并施加严格的工具权限隔离；
3. **任务体量控制 (Task Right-Sizing)**：每个子任务聚焦于单一内聚的功能垂直切片，预期推进轮数保持在 10~20 轮黄金区间，核心修改文件控制在 1~3 个，防止单任务膨胀超过 30 轮；
4. **自包含首轮提示词**：子会话不共享主会话上下文，派发给子代理的首轮提示词（First-Turn Prompt）必须 100% 自闭环，明确“干什么、在哪干、如何测”。

---

## 派发前置四道门禁 (Pre-Flight Gates)

在调用 `invoke_subagent` 之前，主控 Agent 必须依序通过以下四道硬性检查门禁：

## 角色职责与 Harness 物理路由契约

Harness（`SubagentRunner`）根据主控传入的 `role` 字段执行客观路由与权限裁剪：

| 角色标识 (`role`) | 别名支持 | 绑定的 Copilot Agent 与提示词 | 注入的物理工具集 | 核心交付物 |
|---|---|---|---|---|
| `researcher` | `searcher` | 调研 Agent (`cph-researcher-agent-prompt.txt`) | `read_file`, 只读 `run_command`（**绝对无写工具**） | 结构化 Markdown 调研分析报告（含文件路径、行号与根因建议） |
| `coder` | 无 | 编码 Agent (`cph-coder-agent-prompt.txt`) | `read_file`, `patch_file`, `write_file`(受限), `run_command` | 代码微补丁落地与单元测试通过证据报告 |

> 🔒 **全局防御锁**：无论哪个角色，Harness 均从其可用工具中**物理剔除 `invoke_subagent`**。子代理无法调用子代理，彻底阻断递归失控。子代理均挂载 `handoff` 技能，当单个子任务达到 30 轮上限时，由 Harness 调度器自动通过微观交接文档拉起 Successor 子代理透明接力。

## 首轮提示词（First-Turn Prompt）编写标准

### 1. 调研角色 (`researcher` / `searcher`) 首轮提示词规范

必须为 Researcher 提供精准的侦探线索：
- **目标与假设**：需要排查什么现象、验证什么假设；
- **排查入口**：建议从哪些文件、函数或历史提交切入；
- **输出要求**：明确要求输出关键代码行号、真实执行链路与后续重构建议。

**标准模板**：
```yaml
role: researcher
description: 调查 <模块名> 的调用链路与潜在瓶颈
prompt: |
  【调研目标】: 探查 <具体问题/需求背景>。
  【入口文件】: 请阅读 <文件路径A> 中的 <函数名> 与 <文件路径B>。
  【关键关注点】:
  1. 梳理数据从输入到落盘的完整流转过程；
  2. 诊断是否存在竞争冒险、死锁或未处理的异常分支；
  3. 运行只读命令 `<只读检查命令>` 收集现场证据。
  【交付标准】: 输出包含事实结论、涉及核心文件及行号、根因剖析以及给 Coder 的实施建议的 Markdown 报告。
```

---

### 2. 编码角色 (`coder`) 首轮提示词规范

必须为 Coder 划定不可逾越的文件边界与验收标准：
- **修改目标**：需要新增的功能特性或修复的具体缺陷；
- **文件边界**：限定修改的具体文件路径（严格正交，不与其他并发任务重叠，建议 1~3 个核心文件）；
- **补丁约束**：强调采用 `patch_file` 局部精准替换；
- **验收命令**：必须运行的测试命令与期望的输出状态。

**标准模板**：
```yaml
role: coder
description: 修复 <文件路径> 中的 <具体缺陷> 并补充测试
prompt: |
  【实施目标】: 为 <模块名> 修复/实现 <具体功能需求>。
  【涉及文件 (限定范围)】:
  - 核心实现: <文件路径A>
  - 单元测试: <测试文件路径B>
  【改动约束】:
  - 严格采用局部微补丁 `patch_file` 进行最小可行改动，保持既有代码风格；
  - 严禁触碰限定范围之外的文件。
  【验证标准】:
  - 修改后在终端运行 `<具体测试命令，如 bun test tests/xxx.test.ts>`；
  - 确保所有测试用例 100% 绿灯通过，并在交付报告中贴出测试命令输出。
```

## 标准 `invoke_subagent` 调用示例

主控 Agent 在满足四道门禁后，在标准 ```action 块中发起调派：

```action
tool: invoke_subagent
subagents:
  - role: researcher
    description: 探查 AccountPool 在并发下的 Token 轮换机制与限频点
    prompt: |
      【调研目标】: 调查 AccountPool 在并发获取 Token 时的锁机制与避险策略。
      【入口文件】: src/auth/account-pool.ts 与 src/auth/token-manager.ts。
      【关键关注点】:
      1. 分析 getNextAvailableToken 在多并发调用时是否存在竞态条件；
      2. 梳理 429 标记后的退避重试链路。
      【交付标准】: 输出包含行号分析与排错建议的结题报告。
  - role: coder
    description: 完善 session-manager 的边界用例测试覆盖
    prompt: |
      【实施目标】: 为 session-manager 补充会话恢复异常边界测试。
      【涉及文件】: tests/session/session.test.ts。
      【验证标准】: 执行 `bun test tests/session/session.test.ts` 确保全部通过，并汇报测试日志证据。
```

## 常见反模式与红线警示 (Anti-Patterns)

| 反模式 | 严重后果 | 正确做法 |
|---|---|---|
| **❌ 缺失 `role` 字段** | Harness 无法识别目标 Agent，导致调度中断 | 必须显式声明 `role: researcher` 或 `role: coder` |
| **❌ 单个任务体量过大 (>30 轮)** | 子代理中途耗尽轮数，被迫多次交接，上下文损耗 | 遵循 10~20 轮黄金区间，核心修改文件 ≤3 个，大需求分流水线 |
| **❌ 并发 Coder 修改相同文件** | 并发写冲突、后完成的覆盖先完成的，导致代码丢失 | 按文件正交拆分；重叠文件拆分为串行两阶段执行 |
| **❌ 提示词简陋 (“帮我改下登录”)** | 子代理无主会话历史，因上下文缺失而瞎猜乱改 | 编写完整的首轮提示词（背景、文件路径、测试命令） |
| **❌ 让 Researcher 顺手改代码** | 破坏只读边界，易引发未验证的回归错误 | 严格让 Researcher 只输出报告，由后续 Coder 施工 |
| **❌ 忽略测试证据直接裁决** | 盲目信任子代理文本输出，遗漏隐蔽 Bug | 主控必须在收到 Coder 报告中的真实测试绿灯证据后再输出 `FINAL_ANSWER` |
