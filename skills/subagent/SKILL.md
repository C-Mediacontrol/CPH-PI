# Sub-agent 复杂任务正交拆解与并发调度工程指南

> **挂载边界约束**：**本技能仅且必须挂载在【主控 Agent (CPH-Main)】中**。子代理（Researcher / Coder）专注于具体攻坚，不挂载此技能。

---

## 核心原则 (Core Principles)

1. **会话独立与配额倍增**：每个子任务派发给全新的独立会话，享有专属的充足推理预算与干净上下文；
2. **显式角色与工具边界**：每个子任务必须显式指定为 `researcher`（别名 `searcher`）或 `coder`，系统按角色施加严格的工具权限隔离；
3. **任务体量三大物理指标 (Three Physical Sizing Metrics)**：每个子任务聚焦于单一内聚的功能垂直切片，严格依据客观三大物理指标界定规模，杜绝抽象轮数臆测：
   - **指标 1（单核心文件）**：单任务核心修改源文件 ≤1 个，避免跨文件耦合；
   - **指标 2（大文件独占）**：单文件超过 500 行的源文件必须作为独占子任务派发，不得与其合并其它文件；
   - **指标 3（低关注点聚集）**：单任务聚焦 ≤2 个明确技术关注点，保障子代理注意力高度集中；
4. **技能内化与无名化派发铁律 (Internalized Skills & Anonymous Dispatch)**：主控在全局把控并内化专业技能（审查、TDD 测试驱动开发、系统化排错等）；调用 `invoke_subagent` 派发子任务时，**工单 Prompt 中严禁提及任何 Skill 名称**！必须将其解构为具体的物理目标、限定文件路径与验收命令。子代理零 Skill 认知；
5. **自包含首轮提示词**：子会话不共享主会话上下文，派发给子代理的首轮提示词（First-Turn Prompt）必须 100% 自闭环，明确“干什么、在哪干、如何测”。

## 角色职责与工具权限

系统根据主控声明的 `role` 字段自动赋予对应的专项工具集：

| 角色标识 (`role`) | 别名支持 | 职能定位 | 可用工具清单 | 核心交付物 |
|---|---|---|---|---|
| `researcher` | `searcher` | 复杂代码走查、链路逆向、根因分析 | `read_file`, 只读 `run_command`, `write_file` (仅限落盘正式报告/交接) | 结构化 Markdown 调研分析报告（含文件路径、行号与根因建议） |
| `coder` | 无 | 外科手术级精准代码修改与单测验证 | `read_file`, `patch_file`, `write_file`, `run_command` | 代码微补丁落地与单元测试通过证据报告 |

## 技能内化与无名化派发铁律 (Internalized Skills & Anonymous Dispatch)

主控在全局把控并内化所有专业工程技能（如代码质量审查、系统化排错、TDD 测试驱动开发、架构设计等）。向子代理派发工单时，**工单 Prompt 中严禁提及任何 Skill 名称**！

1. **零 Skill 认知契约**：子代理（Researcher / Coder）保持纯粹执行者与攻坚者定位，环境不提供、Prompt 也不灌输任何外部 Skill 概念；
2. **专业技能物理动作解构**：主控必须将高阶技能规范内化为具体的物理动作、限定的目标文件路径、技术关注点与验收验证命令：
   - *TDD 技能内化*：在 Prompt 中明确写出“请先阅读现有单测 `tests/foo.test.ts`，为新逻辑编写失败测试用例，运行 `bun test` 确认红灯；随后在 `src/foo.ts` 中以局部微补丁 `patch_file` 补全实现；再次运行 `bun test` 确保 100% 绿灯”；
   - *代码审查技能内化*：在 Prompt 中明确写出“检查 `src/foo.ts` 中是否存在超过 50 行的长函数、未捕获的 Promise 异常或资源泄漏，并给出具体行号修复建议”；
   - *系统排错技能内化*：在 Prompt 中明确写出“探查 `src/bar.ts` 第 45 行附近状态机的非法状态转移，结合终端输出分析根因”；
3. **严禁抽象指引**：严禁出现“请使用 tdd 技能开发”、“请按 code-review 规范审查”等空洞指令。

## 首轮提示词（First-Turn Prompt）编写标准

### 1. 调研角色 (`researcher` / `searcher`) 首轮提示词规范

必须为 Researcher 提供精准的侦探线索：
- **目标与假设**：需要排查什么现象、验证什么假设；
- **排查入口**：建议从哪些文件、函数或历史提交切入；
- **输出要求**：明确要求输出关键代码行号、真实执行链路与后续重构建议。

**标准模板**：
```yaml
role: researcher
description: 调查 <模块名> 的调用链路与潜在瓶颈
prompt: |
  【调研目标】: 探查 <具体问题/需求背景>。
  【入口文件】: 请阅读 <文件路径A> 中的 <函数名> 与 <文件路径B>。
  【关键关注点】:
  1. 梳理数据从输入到落盘的完整流转过程；
  2. 诊断是否存在竞争冒险、死锁或未处理的异常分支；
  3. 运行只读检查命令 `<只读检查命令>` 收集现场证据。
  【交付标准】: 输出包含事实结论、涉及核心文件及行号、根因剖析以及给 Coder 的实施建议的 Markdown 报告。
```

---

### 2. 编码角色 (`coder`) 首轮提示词规范

必须为 Coder 划定明确的文件边界与验收标准（严格遵循三大物理指标：核心修改源文件 ≤1 个，单文件超过 500 行必须独占，聚焦 ≤2 个关注点）：
- **修改目标**：需要新增的功能特性或修复的具体缺陷；
- **文件边界**：限定修改的具体文件路径（严格正交，核心修改源文件 ≤1 个，单文件超过 500 行独占，聚焦 ≤2 个技术关注点）；
- **补丁约束**：强调采用 `patch_file` 局部精准替换；
- **验收命令**：必须运行的测试命令与期望的输出状态。

**标准模板**：
```yaml
role: coder
description: 修复 <文件路径> 中的 <具体缺陷> 并补充测试
prompt: |
  【实施目标】: 为 <模块名> 修复/实现 <具体功能需求>。
  【涉及文件 (限定范围)】:
  - 核心实现: <文件路径A (核心修改源文件 ≤1 个)>
  - 单元测试: <测试文件路径B>
  【改动约束】:
  - 严格采用局部微补丁 `patch_file` 进行最小可行改动，保持既有代码风格；
  - 严格限定在指定的目标文件范围内。
  【验证标准】:
  - 修改后在终端运行 `<具体测试命令，如 bun test tests/xxx.test.ts>`；
  - 确保所有测试用例 100% 绿灯通过，并在交付报告中贴出测试命令输出。
```

## 标准 `invoke_subagent` 调用示例

主控 Agent 在满足五道门禁后，在标准 ```action 块中发起调派：

```action
tool: invoke_subagent
subagents:
  - stage: 1
    role: researcher
    description: 探查 AccountPool 在并发下的 Token 轮换机制与限频点
    prompt: |
      【调研目标】: 调查 AccountPool 在并发获取 Token 时的锁机制与避险策略。
      【入口文件】: src/auth/account-pool.ts 与 src/auth/token-manager.ts。
      【关键关注点】:
      1. 分析 getNextAvailableToken 在多并发调用时是否存在竞态条件；
      2. 梳理 429 标记后的退避重试链路。
      【交付标准】: 输出包含行号分析与排错建议的结题报告。
  - stage: 1
    role: coder
    description: 完善 session-manager 的边界用例测试覆盖
    prompt: |
      【实施目标】: 为 session-manager 补充会话恢复异常边界测试。
      【涉及文件】: tests/session/session.test.ts。
      【验证标准】: 执行 `bun test tests/session/session.test.ts` 确保全部通过，并汇报测试日志证据。
  - stage: 2
    role: coder
    description: 基于 Stage 1 调研与测试基线修复并发死锁
    prompt: |
      【实施目标】: 修复并发获取 Token 时的锁竞态。
      【涉及文件】: src/auth/account-pool.ts。
      【验证标准】: 执行 `bun test tests/auth/` 确保全部绿灯。
```

## 成果审阅与交付裁决契约
 
1. **派发即提交**：主控输出标准的 `invoke_subagent` 即可，系统会自动保留规划上下文并执行调度，无需额外手动编写规划交接文件；
2. **传引用轻量审阅 (Pass-by-Reference Review)**：子代理交付报告以结构化摘要与落盘产物（如测试报告、分析报告或补丁文件）呈现给主控。底层物理执行细节由 Harness 自动归档至物理账本（`.cph/state/execution-ledger.md`），主控无需倾倒子会话的冗长工具调用历史，按需检索关键产物即可进行交叉验证；
3. **综合审阅与交叉验证**：收到子代理交付报告后，主控负责综合评估各项交付物，并运行必要测试验证整体功能；
4. **成果审阅与 plan.md 物理任务清单打勾对账**：
   - 每次收到子代理交付报告并技术审阅验证无误后，主控必须使用 `patch_file` 将工作区 `plan.md` 物理任务清单对应项由 `- [ ]` 更新打勾为 `- [x]`；
   - 若发生外部不可抗力或逻辑阻断，标记为 `[!] 阻断原因`；
5. **终局收敛闭环门禁**：
   - 只有当工作区 `plan.md` 物理任务清单中的所有规划项均已打勾完成（`- [x]`）或明确标注阻断、且验证充分时，才允许在独立一行输出 `FINAL_ANSWER` 进行终局闭环；
   - 只要 `plan.md` 物理任务清单中仍有未完成的待办项 `- [ ]`，严禁提前收敛或输出 `FINAL_ANSWER`，主控必须继续调用 `invoke_subagent` 派发后续阶段任务攻坚。

## 常见反模式与红线警示 (Anti-Patterns)

| 反模式 | 严重后果 | 正确做法 |
|---|---|---|
| **❌ 缺失 `role` 字段** | 系统无法识别目标角色，导致调度中断 | 必须显式声明 `role: researcher` 或 `role: coder` |
| **❌ 违反三大物理指标（修改多文件、500 行未独占或关注点过多）** | 任务认知超载、子代理中途耗尽轮数，上下文损耗严重 | 严格遵循三大物理指标：单任务核心修改源文件 ≤1 个、>500 行独占、聚焦 ≤2 个关注点 |
| **❌ 并发 Coder 修改相同文件** | 并发写冲突、后完成的覆盖先完成的，导致代码丢失 | 按文件正交拆分；重叠文件拆分为串行两阶段执行 |
| **❌ 提示词简陋 (“帮我改下登录”)** | 子代理无主会话历史，因上下文缺失而瞎猜乱改 | 编写完整的首轮提示词（背景、文件路径、测试命令） |
| **❌ 工单 Prompt 携带 Skill 名称** | 诱发子代理 Skill 幻觉与认知混乱，破坏纯粹执行边界 | 技能内化与无名化派发：Prompt 中严禁提及任何 Skill 名称，解构为物理动作、文件路径与验收命令 |
| **❌ 让 Researcher 顺手改代码** | 破坏只读边界，易引发未验证的回归错误 | 严格让 Researcher 只输出报告，由后续 Coder 施工 |
| **❌ plan.md 物理任务清单未清空即提前早退** | 任务半途而废，违背收敛门禁导致半拉子工程 | 成果审阅必须与 plan.md 物理任务清单打勾对账，清单全部打勾完成前严禁输出 `FINAL_ANSWER` |
| **❌ 忽略测试证据直接裁决** | 盲目信任子代理文本输出，遗漏隐蔽 Bug | 主控必须在收到 Coder 报告中的真实测试绿灯证据并完成 plan.md 对账后再闭环 |
